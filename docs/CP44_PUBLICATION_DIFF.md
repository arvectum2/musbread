# CP-44D — сравнение версий материалов перед локальным релизом

16 октября 2026 · №0372200172326000015 · **внутренний доконтрактный CP-44D**, не приёмка, не разрешение на выпуск музейного сайта. TinyMCE не менялся, расход 0 ₽.

## Сценарий редактора

- В списке MoonShine «Материалы музея» есть действие **«Сравнить»**, а в приватном предпубликационном чек-листе — **«Сравнить версии перед выпуском»**.
- По защищённому адресу `/admin/museum-content/compare` показываются сравнение **текущего набора к следующему экспорту** и **последнего верифицированного локального релиза**: добавленные, изменённые, исчезающие и неизменённые материалы, события и (только для superuser) разделы.
- Для изменённых записей показан перечень полей: название, текст, SEO, метаданные, связи, медиа/документы, перевод, сортировка. Полные версии неопубликованного HTML и закрытых файлов в отчёте **не отображаются**. Переход материала в черновик отражается как «исчезнет из новой версии», а не удаление записи из CMS.
- Редактор без администраторских прав видит материалы только из текущих назначенных ему рубрик, включая фильтрацию архивного снимка по публичному `section_slug`. События доступны по действующим общим правам ресурса «События»; редакционная ACL по событиям остаётся открытой задачей. Изменения общей карты разделов показывает только superuser.
- Указаны SHA-256 двух снимков и ID локальной версии, а также количество критичных замечаний и рекомендаций CP-42D/CP-43D. Сравнение **не производит публикацию**, не ставит задачу в очередь, не переключает ссылки `current/previous` и не меняет содержимое текущего публичного релиза.

## Источник сравнения и защита от фиктивных изменений

1. `scripts/release_site.py deploy` при подготовке проверенного локального релиза дополнительно архивирует оригинальный `published.json` в **приватную** папку `deploy/local/private-snapshots/<sha256>.json` (вне web/out, не копируется в статический сайт). Архив записывается атомарно, с правами файла 0600, а его SHA-256 и длина сверяются с `snapshot-manifest.json`. Если архив повреждён — релиз не переключается. Архивированный снимок привязан к итоговому release manifest.
2. Для уже существующего локального стенда безопасное единоразовое заполнение архива возможно через `python3 scripts/release_site.py archive-current`. Команда сначала полностью проверяет текущий локальный релиз и отказывает, если отслеживаемый CMS `published.json` не совпадает **побайтно** с его манифестом. Это **не новый релиз** и не отмена предыдущей версии. На текущем Mac mini архив заполнен для `5fdbebaf569d5ba884819cc0669962cb5864c82146e3cd5afd07d582f9ceaf2e`.
3. Сервис сравнения проверяет путь текущей локальной версии `current` внутри `releases/<release-id>`, пересчитывает идентификатор релиза и контрольные суммы **всех файлов** по `release-manifest.json`, а затем проверяет SHA-256 и размер приватного JSON-архива. **Если базы нет, сравнение не утверждает, что все записи добавлены/удалены** — показывает понятное предупреждение «нет подтверждённого базового снимка».
4. Подготовленная версия формируется точно существующим `museum:export`, но со **всеми** выходными путями в новой случайной директории ОС (включая JSON, манифест, медиа и документы). Проверяется SHA-256, временная директория автоматически очищается, штатные `apps/web/src/data/published.json`, релизные ссылки и CMS-записи не перезаписываются. Это вычисление по актуальным данным, а не «публикация сайта».
5. Сопоставление использует стабильный ключ `(type, slug)` для материалов и `slug` для событий/разделов. **Переименование slug** будет представлено как «удаление старого адреса + добавление нового» — это правильно для маршрутов, но не попытка распознать редакционную идентичность.

## Проверки и ограничения

- `MuseumPublicationDiffTest`: отсутствие базы, изменения/добавления/исчезновения по всем трём сущностям, изменение только определённых полей, скрытие чужих разделов Editor, приватный HTTP и отсутствие мутаций очереди/рабочего published.json, порча исходного снимка/манифеста.
- `tests/test_release_site.py`: приватное архивирование с проверкой прав, отсутствие JSON архива в webroot, повторное архивирование, отказ на подмене снимка и контроль rollback.
- `scripts/qa_cms_browser.py` создаёт базовую версию исключительно из временного CMS seeded snapshot в **изолированном** контуре и проверяет в реальном браузере добавленную новость/событие и переход к чек-листу. QA-файлы удаляются после прогона.
- Снимок «текущая версия» относится **только к локальному стенду**, не к неизвестному реальному публичному серверу музея. Предконтрактный анализ не устанавливает реальный боевой deploy или правовой факт приёмки.
- Это **семантическое сравнение CMS-контента и разделов**, а не CSS, ассетов сборки, SEO индексирования, доступности реальных внешних API или инфраструктуры. Их контролируют отдельные существующие скрипты и CI. При экспорте изменённые изображения считаются изменениями поля `media`; сравнение не содержит личных данных сотрудников музея.
- Нет автоматического создания архивов при «обычном CMS-экспорте», который сам по себе не является релизом. Нет дополнительной базы данных или платных сторонних сервисов.

## Дополнение TZ-106: журнал сохранённых локальных релизов (17.10.2026)

`python3 scripts/release_site.py history --dest deploy/local` — новое **читающее** действие существующего скрипта, перебирающее и проверяющее SHA-256 всех release-manifest из существующих локальных `releases/`. Показывает ID, роли current/previous/archived, объём и число файлов. Повреждения и посторонние symlink приводят к ошибке. На Mac mini проверено **10/10** сохранённых локальных релизов; при этом текущие/предыдущие ссылки и опубликованное содержимое не менялись. Это не история на сервере музея и не разрешение удалять архив. Политика хранения и физическая сеть остаются на согласование.
