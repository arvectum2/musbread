## Проверка первоисточника и аналогов

Прямым HTTP-доступом с Mac mini проверены страницы https://muzei-xleb.ru/ , https://www.spbmuseum.ru/ и https://rusmuseum.ru/ : все HTTP 200. Эти публичные страницы показывают структуру музейного сайта, **но не раскрывают внутренние кеши, SQL/ORM, политики редакторского доступа и требования к кабинетам**. Применять чужую внутреннюю архитектуру или домысливать функциональность по аналогам нельзя. Авторитетным источником backend-обязательств остаётся оригинальное ТЗ; источником фактического исполнения — Laravel-код и запущенные тесты.

## TZ-215: не дублировать существующие средства защиты

Уже существуют Laravel 13/Eloquent, стандартный CSRF middleware MoonShine, аутентификация и ACL по разделам, входной throttling, ORM-запросы с валидируемыми параметрами, SQL-подобные негативные тесты, браузерный сценарий на изолированной SQLite с реальной HTTP-сессией. Новая система авторизации/очистки SQL **не добавлена**.

Фактическое исправление: в `MuseumEntryResource` счётчик связанных событий теперь ограничен `editableBy($user)`, как и счётчик других материалов. В `MuseumEntryIndexPage` фильтр по наличию связей также учитывает права доступа к связанным событиям. Раньше редактор мог косвенно узнать количество связанных событий в чужом разделе (без текста) и фильтровать по факту чужой связи; теперь эта информация закрыта. Суперпользователь сохраняет полный просмотр.

Добавлены тесты SQL-подобных идентификаторов разделов и поискового запроса, отказа в просмотре скрытых материалов и неизменности числа записей. В **существующий**, а не новый браузерный набор включены проверки: 419 при POST без CSRF на перестановку разделов, 404 для поддельного event ID; прежняя проверка 419 на медиатеку сохранена.

## TZ-217: проверить уже включённое кеширование

В `apps/cms/.env.example` уже задан `CACHE_STORE=database`; миграция создаёт `cache` и `cache_locks`. Существующие публикационные задачи используют Laravel `Cache::lock` для исключения параллельных выгрузок, `RateLimiter` использует Laravel cache. Кеширование **не** используется как источник разрешений/публикуемости разделов, чтобы не допустить отложенного отзыва права редактора.

Создана диагностическая CLI-команда **`php artisan museum:cache-check --require-shared`**. Она:
- проверяет запись и чтение в уже заданном cache store с коротким TTL;
- проверяет невозможность двух одновременных владельцев одного lock и успешный перехват после освобождения;
- работает на случайных временных ключах, не трогает реальные публикации, разделы и ключи пользователей; очищает след;
- в режиме `--require-shared` отказывает при process-local `array`, `file` и других неутверждённых многосерверных хранилищах. Этот режим не гарантирует фактическую сетевую достижимость Redis/БД в боевой сети, её проверяют после развёртывания.

На Mac mini с локальным `database` команда успешно пройдена. Тесты на базе SQLite отдельно подтверждают сохранность реального lock `museum:publication-export` и отсутствие оставшихся диагностических ключей. Без флага локальный `array` допускается только для unit/однопроцессных сценариев, не для production worker.

## TZ-219: сознательно не создавали личный кабинет

На действующем сайте нет публичного подтверждения обязательности кабинета, логина посетителя и многошаговых заявок. В формулировке реестра условие «если нужны» прямо указано. В прототипе есть Next.js-компоненты и закрытые административные формы MoonShine, но **нет** личного кабинета посетителя. Дополнение будет допустимо только при выявлении отдельной обязанности в оригинальном ТЗ или согласованном решении музея, с отдельной моделью персональных данных и прав. Пока TZ-219 = **Нет**, ожидает уточнения заказчика, а не внутренней очереди произвольной разработки.
