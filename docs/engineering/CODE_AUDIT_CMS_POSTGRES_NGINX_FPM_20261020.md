# CODE-AUDIT-09 — PostgreSQL и Nginx → PHP-FPM → Laravel

**20.10.2026.** Всё выполнено на Mac mini, в проекте MusBread на ArvectumSSD. Использовались исключительно одноразовые Docker PostgreSQL 16 и контейнеры Nginx/PHP-FPM с отдельной пустой БД и тестовыми пользователями. Нет push, деплоя, новых вопросов музею, изменений оригиналов, доменов, ЕИС, БД и Docker-контейнеров других проектов.

## PostgreSQL: найден и устранён миграционный дефект

MoonShine первоначально создаёт роль Admin с явным ID=1, не продвигая PostgreSQL serial sequence. Следующая миграция пытается автоматически создать роль Editor с тем же ID и при чистой установке PostgreSQL падает с конфликтом ключа.

Добавлена миграция 2026_10_15_125000_realign_moonshine_pg_role_sequence.php. Она только на PostgreSQL синхронизирует pg_get_serial_sequence c текущим MAX(id), не переписывая роли и назначения пользователей. На SQLite/MySQL ничего не меняет; откат последовательности не делает, чтобы не породить дубликаты первичных ключей. После исправления **45 миграций нового PostgreSQL 16 прошли**.

## PostgreSQL: реальные многопроцессные гонки

Новые scripts/qa_shared_museum_entry_postgres.py и scripts/qa_shared_museum_entry_pg_worker.php создают чистую отдельную базу PostgreSQL, опубликовав порт БД только на 127.0.0.1, и синхронно запускают два независимых PHP процесса. Оба пытаются сохранить разный текст одного материала в общей БД через MuseumEntryRevisionGuard и SQL compare-and-swap edit_version, внутри транзакции.

**8/8 испытаний PASS:** ровно одна успешная запись, ровно один HTTP 409, итоговая редакция соответствует победителю, потерянных правок нет. Ранее аналогичные проверки SQLite прошли 15/15, однако только этот этап подтвердил PostgreSQL. Конкуренция проверена в отдельных PHP CLI-процессах с общим SQL guard, но не с двух браузерных HTTP-сессий одновременно.

Контейнер PostgreSQL и его данные удалены по завершении. Ранее существующие контейнеры/базы Arvectum не менялись.

## Реальный Nginx → FastCGI → PHP-FPM → Laravel

Добавлен scripts/qa_cms_nginx_fpm_docker.py. Он создаёт временную SQLite в закрытом каталоге на ArvectumSSD, выполняет 45 миграций, создаёт фиктивного админа со случайным паролем и запускает отдельные Docker-контейнеры nginx:stable-alpine и php:8.4-fpm-alpine в выделенной Docker bridge-сети. HTTP публикуется **только на 127.0.0.1**; порт FPM и БД не опубликованы. Сеть выделена, но исходящий доступ контейнеров полностью не блокировался. Никакие реальные музейные пароли и данные не использовались.

Через настоящий Nginx и FastCGI получены: GET /up=200, GET /admin/login=200, закрытый /admin/museum-documents без входа=302, GET приватного /storage/museum/...=404, /.env=403. Далее тестовый администратор проходит **настоящую страницу входа с CSRF-токеном и POST /admin/authenticate**, получает session cookie и GET /admin/museum-documents=200.

Профили HTTP нагрузки содержали и публичные запросы, и гостевые запросы к закрытому разделу, и обращения с реальной авторизованной сессией. **96/96 PASS**, из них 32 с авторизацией, 32 гостевых и 32 публичных.

Это локальный стенд, не боевой SLA. Все временные Docker-контейнеры, сети, тестовые DB и сессии были удалены; скачанный образ PHP-FPM остался в стандартном Docker-хранилище.
