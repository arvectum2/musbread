# CODE-AUDIT-08 — сохранение общей редакции + локальный HTTP/PHP-FPM

**20.10.2026.** Испытания проведены только на Mac mini в репозитории MusBread на ArvectumSSD, в отдельных синтетических SQLite-базах и с локальным PHP-FPM. Музейный сервер, домен, БД заказчика, исходные материалы ЕИС и production CMS не изменялись. Push/deploy не выполнялись. Новых вопросов музею нет.

## Обнаруженная подтверждённая гонка

MoonShine раньше позволял двум редакторам сохранить одну запись по очереди без проверки версии открытой формы. Добавленный на первом шаге отпечаток редакции и SELECT FOR UPDATE защитил последовательное сохранение двух пользователей в одном тестовом процессе, но отдельное многопроцессное испытание реальной общей файловой SQLite-БД **дважды зафиксировало возможность успешных ответов обеих операций** без атомарного SQL-права на ту же редакцию. Этот дефект был выявлен и исправлен до коммита. Проблема не объявлялась доказанной для настоящего музея: его БД не использовалась.

## Итоговое исправление

1. В MoonShine MuseumEntryFormPage добавлено скрытое поле с SHA-256 отпечатком открытой редакции. Это значение не записывается в музейную модель. Источник отпечатка — существующий MuseumApprovalRevision, который учитывает данные страницы и связанные изображения, документы, видеовставки и ссылки.
2. MuseumEntryResource сохраняет через транзакцию. Перед изменением формы сохраняется приоритет проверки SectionAccess: чужой раздел по-прежнему возвращает 403, даже если токен не указан.
3. Новый MuseumEntryRevisionGuard в рамках той же транзакции сверяет SHA-256 и атомарно резервирует текущую версию оператором SQL UPDATE ... WHERE edit_version = expected с инкрементом edit_version. Если текущую версию уже забрал другой процесс, операция завершается конфликтом и не применяет устаревшую форму.
4. Миграция 2026_10_20_110000_add_edit_version_to_museum_entries.php добавляет целочисленный edit_version со значением 0 по умолчанию для существующих записей. Это не пользовательский реквизит, не смена URL, не произвольная новая редакция музейных материалов. Статический экспорт продолжает пользоваться установленной явной схемой полей; отпечаток одобрения становится консервативнее после правок.
5. После HTTP 409 редактор должен заново открыть форму, увидеть обновлённые данные и лишь затем сохранить новую правку. Автоматического слияния конфликтующих текстов нет.

## Доказательства

**Форма CMS:** MuseumEntryOptimisticLockTest: Алиса и Боб открывают один и тот же материал, первая правка сохраняется, вторая устаревшая отвергается HTTP 409 и не меняет содержимое; новый отпечаток позволяет новой правке Боба быть сохранённой. Пустой/поддельный токен — 409. Проверка формы и существующих прав редакторов PASS.

**Реальная общая БД:** scripts/qa_shared_museum_entry_race.py создаёт одноразовый SQLite-файл в .local_archive, запускает миграции и две самостоятельные PHP-процедуры в разных ОС-процессах. Оба процесса ждут общего барьера и почти одновременно вызывают тот же MuseumEntryRevisionGuard внутри транзакции, затем пытаются сохранить одну и ту же запись. Проверяется ровно один успешный коммит, один конфликт 409/SQLITE_BUSY и соответствие итоговой записи победителю.

- Изначальные 3 раунда после SQL-CAS — PASS.
- Дополнительные четыре полных повторения по 3 раунда — PASS.
- **15 из 15 раундов: ровно один коммит, ровно один отказ, 0 потерянных изменений.**
- SQLite lockForUpdate не является полноценной построчной блокировкой: SQL-CAS защищает запись, а часть проигравших транзакций сообщает SQLITE_BUSY. В PostgreSQL/MySQL ожидается конфликт версии после освобождения блокировки, но эти серверы в настоящем испытании не использовались.
- Сценарий проверяет настоящий shared-file DB race и общий guard, но не настоящий HTTP-запрос MoonShine двумя ОС-процессами; одно-процессный HTTP feature test формы проведён отдельно.

## Временный PHP-FPM по локальному HTTP

scripts/qa_cms_local_fpm_http.py создал **изолированный** PHP-FPM пул из 3 child-процессов, приватный Unix-сокет и одноразовую мигрированную SQLite-БД; тестовый HTTP-шлюз был доступен ТОЛЬКО на 127.0.0.1. Привилегированные маршруты или реальные музейные пароли не применялись; запрашивались /up, /admin/login и /admin/museum-documents.

Результат: **96 из 96 HTTP-запросов с ожидаемым результатом**. Для /up получен HTTP 200; для закрытого /admin/museum-documents — HTTP 302 для гостя. Пул PHP-FPM реально обрабатывал Laravel, но шлюз тестовый, **не Nginx, не HTTPS, не авторизованные скачивания**. Цифры p95 — только локальный стенд без штатного production reverse proxy.

## Остаточная инженерная очередь

- Испытать миграцию и блокировку на конкретной production-подобной DBMS (PostgreSQL или MariaDB), а не только SQLite, и при действительных двух авторизованных браузерных сессиях.
- Провести end-to-end CMS по настоящей локальной Nginx + PHP-FPM конфигурации с HTTPS/cookies, нагрузкой на авторизованное скачивание PDF и полноценным TLS/токеном.
- Добавить UX сравнения двух версий и разрешения конфликтов редактором: сейчас 409 предотвращает потерю данных, но вручную требуется повторно открыть страницу.
- Проверить нагрузку, память, ограничения PHP-FPM и race-поведение на предоставленной после договора инфраструктуре. Возможность физического power-loss всё ещё не доказана.

Итоговый договорной светофор: **325 пунктов ТЗ: 85 готово / 118 частично / 122 не готово**. Правки — инженерная безопасность и тестовое покрытие, не новый клиентский acceptance.
