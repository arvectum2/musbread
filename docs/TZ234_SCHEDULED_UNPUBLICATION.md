# TZ-234 — назначенная публикация и автоматическое снятие с публикации

16 октября 2026. Основание: **п. 2.2.3.7.2, строка 276** исходного ТЗ по закупке №0372200172326000015, приоритет **P0**, позиция `TZ-234` первичного `docs/tz-audit/requirements.psv`. Проверено до изменений кода. Не является инициативой CP-52D или необязательным улучшением.

## Реализовано без контрактных допущений

- В MoonShine для **каждой страницы/новости/экскурсии/выставки/страницы документов** и **события афиши** есть необязательное поле **«Снять с публикации (дата и время)»**. Уже существующее поле «Публиковать с» осталось; валидатор проверяет `unpublish_at > published_at`, если указан период. `status = draft` всегда запрещает публичную публикацию.
- Миграция `2026_10_16_230000_add_unpublish_at_to_museum_content` добавляет `unpublish_at` в `museum_entries` и `museum_events`. У всех старых записей поле `NULL`, они работают точно как раньше; никакого массового изменения статусов, удаления и повторной записи контента. Файлы и черновики остаются в **приватной CMS**.
- Отбор в **любой следующий snapshot** един: `status=published` И `published_at <= now()` И (`unpublish_at IS NULL` ИЛИ `unpublish_at > now()`). На точной границе `unpublish_at` материал исключается. События также исключаются, но **дата окончания выставки `ends_at` из TZ-154 не равна времени снятия с публикации**: прошедшие мероприятия остаются в архиве, пока редактор отдельно не назначил прекращение публикации.
- Статус `expired` / «Снято по установленному сроку» отображается в отчёте preflight и фильтре списка материалов. Снятые записи **не учитываются как готовые** и не входят в публичные страницы, связи, изображения и документы при следующей сборке. Запланированные на будущее записи не появляются раньше времени.
- Strict preflight проверяет ссылки активных материалов. Если после снятия с публикации другие страницы продолжают ссылаться на его URL, **экспорт с `--preflight-strict` останавливается до записи**, пока редактор не исправит ссылки. Запись сохраняется в закрытой CMS для восстановления и аудита. Некорректные границы дат отображаются редактору как ошибки.
- **Фактическое удаление уже размещённого статического HTML** выполняется только при очередной передаче и чистом развёртывании нового снимка, а не в секунду истечения времени на клиенте. Локальный Laravel Scheduler готовит выгрузку **раз в час** без пересечения запусков (TZ-104). Ни боевой канал, ни публикационный сервер музея сейчас недоступны; фактический SLA 60 минут не подтверждён.

## Проверки

- `MuseumPublicationExpiryTest`: до и ровно в момент истечения, сохранение приватной записи, старт в будущем, запрет преждевременной публикации, устойчивость постоянных записей и проверка checksum JSON, сломанные внутренние ссылки после снятия блокируют строгий экспорт.
- Изолированный browser QA: новые поля отображаются в реальном редакторе MoonShine для новости и события; редактор TinyMCE без изменений.
- Полный PHPUnit, Python-проверки контрактов и эталонного JSON, frontend Playwright, статический аудит и GitHub Actions. База тестирования — отдельная временная SQLite; реальный JSON `apps/web/src/data/published.json` не переписывается.

## Что ещё требуется для «Да»

Реальная инфраструктура заказчика (две машины, выделенный канал), действительные учётные записи и права, правила сохранения SEO/редиректов, фактическая проверка смены публичных URL при часовом расписании, UAT. В CMS-разделах (узлах навигационного дерева) даты публикации не предусмотрены — дерево контролируется только `status`, его расширение следует согласовать с музеем. Поэтому **TZ-234 остаётся «Частично»**, без заявления об эксплуатации и клиентской приёмке.

Затраты — 0 ₽, TinyMCE не изменён, домен и публичный сервер музея не затронуты.
