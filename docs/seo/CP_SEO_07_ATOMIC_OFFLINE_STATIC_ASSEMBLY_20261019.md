# CP-SEO-07 · сборка сайта без потери музейных оригиналов

19.10.2026. **Сайт музея не изменён, DNS не тронут, продакшн выпуск запрещён до договора.**

## Обнаруженная ошибка в старом порядке команд

Наша рабочая сборка Next.js через `npm run build` автоматически пересоздаёт `apps/web/out`. При этом **101 оригинал PDF/DOCX (287,96 МиБ), 259 исходных URL музейных фотографий (255 статических файлов, 35,49 МиБ) и 27 отдельных HTML архивной пагинации новостей** были сохранены в локальном `out` *после предыдущей сборки* из проверенного личного архива на ArvectumSSD. При очередном `npm run build` эти файлы были удалены из `out` и 56 Python-аудитных тестов обнаружили **массовое отсутствие оригиналов**. Это не означает, что потеряны сами оригиналы: они остаются в `.local_archive` на ArvectumSSD и по-прежнему имеют проверенные SHA-256.

## Исправление эксплуатации без нового дизайна

Добавлен единый [офлайн-скрипт сборки и сверки](../../scripts/build_complete_museum_static_release.py):

```sh
cd /Volumes/ArvectumSSD/arvectum/repos/musbread
.venv/bin/python scripts/build_complete_museum_static_release.py --build
```

Он всегда выполняет операции **в правильной последовательности**: настоящая Next.js production build → восстановление PDF/DOCX **точно по оригинальным SHA-256** → локальная публикация self-hosted копий фото → восстановление 27 статических индексных страниц из собственных исходников музея → *повторная строгая проверка* исходных байтов, объёмов, ссылок и `noindex`. По окончании печатает сводку `MUSEUM_COMPLETE_LOCAL_ARTIFACT_PASS`. Если хотя бы один файл или снимок исчезнет/изменится, команда возвращает ошибку и сборку нельзя считать завершённой.

Для проверки уже существующей сборки без её изменения:

```sh
.venv/bin/python scripts/build_complete_museum_static_release.py --verify-only
```

**Не делать просто `npm run build` и считать `out` готовым к передаче.** Никаких живых ссылок на старые JPG/Drupal, файлы непосредственно копируются и проверяются из нашего архива. В Git репозиторий не попадают тяжёлые и приватные архивы, а значит обычный GitHub CI без подключённого ArvectumSSD *не доказывает* полноту содержания после миграции. Производственная задача после договора — подключить ту же сборочную последовательность к утверждённой площадке доставки, при этом перенести/принять 101 оригинальный документ и 255 изображения.

## Предконтрактный контроль

После восстановления вручную прогнаны QA: **56/56 Python-тестов** (включая 555 старых URL, 881 nginx redirects, 101 документа, 27 архивных страниц, 259 URL фотографий), `--verify-only` проверил 101 PDF/DOCX, 259 фото и 27 страниц, robots.txt `Disallow: /`, пустую XML-карту сайта. По внутреннему SEO аудиту всё ещё **NO-GO**, так как nginx-перенаправления 881 правил подготовлены, но не были развёрнуты и проверены на сервере музея; оригинальная индексация не подвергалась риску. **Полный новый `--build` выполнен и завершён PASS**: Next.js заново очистил `out`, скрипт восстановил все 101 документа, 255 уникальных изображения и 27 индексных страниц, затем по SHA-256 подтвердил байты файлов и запрет индексации предпросмотра. Это не равно технической готовности живого cutover до установки и проверки Nginx на инфраструктуре музея.

Ни одно состояние в матрице 325 требований не меняется только от улучшения локального процесса сборки — это страховка уже перенесённого содержимого.
