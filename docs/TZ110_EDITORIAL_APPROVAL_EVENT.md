# TZ-110 — отдельное одобрение редакции перед закрытой выгрузкой

Дата 17.10.2026, закупка 0372200172326000015. Исходное ТЗ: пункт 2.2.3.5, строка 162 — не более 60 минут от фактического одобрения материала редактором до его публичной видимости.

## Зачем потребовалась отдельная операция

Существующие поля status=published и published_at не являются достоверной меткой фактического решения редактора: последнее также задаёт запланированное время публикации. Фоновая выгрузка JSON и успешное завершение задания не гарантируют появления страницы на публичном сервере.

## Что теперь реализовано

На существующей закрытой странице предпубликационной проверки CMS появилась кнопка «Одобрить эту редакцию и запросить закрытую выгрузку». Она видна только администратору MoonShine, при включённых параметрах MUSEUM_ENABLE_APPROVAL_QUEUE=true и MUSEUM_USE_PUBLISH_QUEUE=true, постоянной database/redis-очереди и общем database/redis cache/lock, успешной проверке опубликованных материалов.

Запрос POST защищён аутентификацией и Laravel CSRF. Сервер повторно загружает сохранённую редакцию, формирует SHA-256 её полей, документов, медиа и связей и сравнивает с отпечатком из предпросмотра. Изменившаяся редакция вызывает HTTP 409. Черновики, публикации с будущей датой, просроченные материалы и критические ошибки блокируются HTTP 422.

Создаётся отдельная приватная запись museum_content_approvals с actor ID, ID материала, SHA-256 редакции, реальным временем UTC, статусом постановки в очередь и publication_run_id. Повторное нажатие не меняет первоначальный approved_at и не дублирует запуск. Запуск приватной выгрузки происходит после записи одобрения в базу. При ошибке очереди сам факт одобрения остаётся сохранённым, статус failed, ответ HTTP 503; повтор допускает восстановление.

Добавлен закрытый журнал /admin/museum-content/approval-journal, доступный только администратору. Он показывает последние 100 записей без текстов черновиков, имеет no-store, noindex и ограниченную CSP. Обычное редактирование, смена status=published и почасовой cron не создают события одобрения.

**Безопасное значение по умолчанию:** MUSEUM_ENABLE_APPROVAL_QUEUE=false. Новая миграция лишь создаёт таблицу и не включает фоновые задания на Mac mini или серверах музея.

## Этап 17.10.2026: обязательный отказ выгрузки без одобрения (только opt-in)

Добавлен серверный `MuseumExplicitApprovalGate`, который используется **в каждой ветке** команды `museum:export`: вручную, по расписанию и из фонового `PublishMuseumSnapshot`. При включённом `MUSEUM_ENABLE_APPROVAL_QUEUE=true` экспорт разрешён лишь для опубликованных `MuseumEntry` с **совпадающим текущим SHA-256 редакции** и завершённой постановкой одобрения в очередь. Изменение текста, SEO, связей, подписи/подробного описания изображения, реквизитов документа или доступности вложения меняет отпечаток (v2) и требует новой редакционной операции.

Сейчас нет отдельной формы одобрения для `MuseumEvent`, `MuseumSection`, общей карточки контактов и SEO фиксированных страниц. **Если среди них есть опубликованные записи, строгий режим полностью отказывает в экспорте** — без молчаливого обхода. В рабочем режиме без opt-in старый прототип работает по-прежнему; экспериментальный режим не включён на Mac mini и не готов для наполненного сайта музея. При opt-in отключена периодическая публикация по часовому scheduler: только явное редакционное действие создаёт новое задание, recovery-задача сохраняется.

До изменения выходных JSON и manifest выполняется проверка, затем повторная сверка по окончании сборки payload. Отказ до подготовки вложений сохраняет текущие файлы; повторная проверка перед записью не равнозначна транзакционному снимку всей БД. Для реальной гарантии отсутствия гонок ещё нужна неизменяемая версия полного среза и проверка конкретного опубликованного HTTPS-релиза.

Проверено локально на базе синтетических записей в автоматических PHP-тестах. Реальный заказчик не давал одобрения и не предоставлял промышленный межконтурный канал; 60 минут остаются **неподтверждёнными**.

## Этап 17.10.2026: одобрение событий, разделов и контроль редакции

**Требование:** исходное ТЗ п. 2.2.3.2 (строка 140) — публикация и проверка достоверности редактором; п. 2.2.3.4 (строки 156–158) — публикация раз в час или по событию, контроль версий и checksum; п. 2.2.3.5 (строка 162) — задержка не более 60 минут после одобрения. В ТЗ нет отдельного требования к сервису immutable snapshot. Мы используем существующий версионный механизм релизов и не вводим новый сервис/БД.

Для MuseumEvent и MuseumSection добавлены явные действия одобрения в существующей защищённой странице проверки CMS. Общие CSRF, права администратора, persistent очередь, время UTC, SHA-256 и приватный журнал. Одна минимальная миграция добавляет два необязательных subject ID в прежний реестр одобрений, не уничтожая историю MuseumEntry. Не создаётся дополнительная панель.

В экспериментальном режиме MUSEUM_ENABLE_APPROVAL_QUEUE=true выгрузка требует точного одобрения каждого опубликованного материала, события и раздела. Для события учитываются связанные материалы и атрибуты обложки, для раздела — сохранённые поля навигации. Черновики, скрытые родителями разделы, недействительные сведения, редактор без права одобрения и изменённые версии блокируются. Глобальные контакты и фиксированный SEO (не имеют пока отдельного approval UI) всё ещё вызывают строгий отказ.

До подготовки выгрузки вычисляется SHA-256 отсортированного набора всех одобренных редакций, после подготовки и перед записью JSON этот **тот же набор** проверяется снова. Даже замена одной уже одобренной редакции другой одобренной версией между проверками вызывает отказ. Это проверка согласованности, а не неизменяемый снимок всей файловой системы или транзакционная изоляция файлов медиа. Полная атомарность промышленного выпуска по-прежнему проверяется отдельно.

Проверено синтетическими PHP-тестами: создание одобрений трёх типов, общий CLI-экспорт и worker, сохранение прежнего пакета при отказе, запрет черновика и устаревшего fingerprint, раздел со скрытым родителем, права CMS, смена версии в процессе сборки. Режим выключен до согласований с музеем.

## Блокеры полного исполнения TZ-110

1. Серверный gate теперь охватывает MuseumEntry, MuseumEvent и MuseumSection. Для опубликованной глобальной карточки контактов и фиксированного SEO полного workflow пока нет — сохраняется строгий отказ. Перед включением на реальном наполненном сайте согласовать редакционные роли и необходимость отдельного одобрения этих типов.
2. Двойная сверка теперь сравнивает исходный набор всех трёх одобренных типов, но не обеспечивает транзакционно неизменяемый полный срез БД/медиа при записи файлов. Для production остаётся испытать изолированную сборку и атомарное обновление всех артефактов, а также связать их с фактическим HTTPS-релизом.
3. Утверждённая редакция ещё не проходит через подтверждённый выделенный межконтурный канал музея к публичной странице. Нет независимого подтверждения появления конкретной версии по HTTPS и доказательства задержки менее 60 минут.
4. С музеем надо согласовать роли утверждающих, повторное утверждение при правках, правило снятия с публикации и процессы вне рабочего времени.
