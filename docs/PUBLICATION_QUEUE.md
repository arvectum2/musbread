# MusBread — очередь публикаций

## Что готово в предконтрактном прототипе

- Laravel database queue, собственная очередь museum-publish.
- Команда museum:queue-export создаёт запуск со статусом queued и ставит одно задание, повторно не добавляет аналогичное при незавершённом предыдущем.
- Job PublishMuseumSnapshot: системный lock до 20 минут, до 3 попыток, команда museum:export, SHA-256 по манифесту, обновление queued/running/succeeded/failed.
- Закрытый журнал museum_publication_runs в MoonShine «Запуски публикации», доступен только Admin и только на чтение.
- Тесты корректного запуска, повторного вызова, ошибок, контроля доступа к журналу.

## Включение позже

По умолчанию MUSEUM_USE_PUBLISH_QUEUE=false. Laravel Scheduler выполняет уже действующий безопасный museum:export напрямую каждый час. Ничего не меняется без явного разрешения.

После настройки постоянной очереди/сервисов:
1. Убедиться, что настроен DB backend, доступна таблица jobs и cache locks.
2. Указать MUSEUM_USE_PUBLISH_QUEUE=true на закрытом сервере CMS и пересобрать конфиг Laravel.
3. Перед запуском выполнить php artisan museum:cache-check --require-shared --require-queue-worker (проверяет очередь, окно retry и shared cache/lock). Worker systemd запускает php8.4 artisan queue:work database --queue=museum-publish --sleep=3 --tries=3 --timeout=540 --backoff=30. Не ставить timeout=900 при DB_QUEUE_RETRY_AFTER=900: per-job timeout=540 < общий lock TTL=840 < DB_QUEUE_RETRY_AFTER=900; после падения worker повторная выдача происходит только после истечения блокировки.
4. Установить и активировать один штатный infra/systemd/musbread-scheduler.timer (раз в минуту) и его oneshot сервис. Не добавлять второй cron. Наблюдать systemctl status и journalctl в закрытом сегменте.
5. Провести UAT журналов, retry/backoff, принудительного и штатного завершения worker, ошибок, мониторинга отказов, версионирования и восстановления на согласованном сервере.
6. Убедиться, что локальные выходные пути команды museum:export (по умолчанию ../web/src/data и ../web/public/media) имеют отдельное разрешённое пространство записи внутри закрытого сегмента. При ProtectSystem=strict и текущих ReadWritePaths такой путь на сервере по умолчанию может быть недоступен. Публичный контур и транспорт требуют отдельного утверждения: без них не запускать фоновые сервисы.

Это **только формирование проверенного пакета контента** внутри CMS. Сетевой транспорт к публичному статическому серверу, согласованные ключи, оператор и разрешения музея не реализованы и не должны предполагаться работоспособными.

Не запускать постоянный worker на пользовательском Mac mini только ради предконтрактной подготовки.


## 17.10.2026 — защищённая кнопка подготовки публикации

Администратор видит на странице предпросмотра кнопку «Опубликовать — подготовить пакет в очереди» **только** при включённых постоянных database/redis-очереди и общем cache/lock (database/redis), без критических ошибок preflight. Запрос защищён CSRF, проверкой SuperUser, повторный enqueue не создаёт активный дубль. При неправильной конфигурации ответ 409, при ошибках опубликованного контента — 422. Три изолированных PHP-теста (32 проверки).

Кнопка создаёт **задание частного экспорта**, не выполняет сквозной выпуск на публичный сервер. По умолчанию MUSEUM_USE_PUBLISH_QUEUE=false, и ничего запускать в фоне на Mac mini не требуется. До настройки выделенного транспорта, доверенной проверки SHA-256, закрытого staging и производственного контроля не переключать конфигурацию. Подробности: [TZ104_107_PUBLICATION_PIPELINE.md](TZ104_107_PUBLICATION_PIPELINE.md).
