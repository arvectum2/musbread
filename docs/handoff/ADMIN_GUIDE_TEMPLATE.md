# TZ-315 · Руководство администратора MusBread (рабочая редакция)

**Статус:** проект документации действующей разработки, 17.10.2026. Не утверждён музеем, без адресов боевой CMS, скриншотов окончательной версии и актов обучения. Не заменяет проект сетевой инфраструктуры.

## Назначение и границы
- CMS: закрытый Laravel / MoonShine; публичная часть: статический Next.js. Не делайте Laravel, БД, файлы медиа и приватные отчёты доступными через публичный Nginx.
- **Администратор** отвечает за роли, структуру, проверку выпуска, восстановление и эскалацию; **редактор** работает в пределах назначенных разделов. Фактические имена сотрудников и матрица доступа заполняются только заказчиком.
- Адрес административного контура и способ доступа предоставляются музеем: **[указать после развёртывания]**. Никаких реальных логинов/секретов в этом руководстве.

## Учетные записи и доступ
1. Получите согласованный закрытый сетевой доступ и индивидуальную учётную запись. Не передавайте пароль по электронной почте или через общие документы.
2. В закрытом MoonShine используйте ресурсы пользователей и ролей. Назначайте право редактора только на реально закреплённые разделы; проверьте доступ под отдельной тестовой учётной записью. Эти же гранты относятся к событиям раздела; события без раздела доступны только администратору.
3. При кадровых изменениях блокируйте/отзывайте доступ по процедуре музея; проверяйте журнал действий `/admin/museum-activity`.
4. Загрузка документов и медиа требует отдельного контроля прав. Публичная статика не должна давать скачивать неопубликованные файлы.

## Подготовка и выпуск материалов
1. Проверяйте структуру `/admin/museum-sections/tree`, особенно статус родительского раздела и черновики, созданные по ТЗ без источника.
2. На `/admin/museum-content/preflight` проверьте ошибки материалов, событий и внутренних ссылок; редактор может исправить содержимое без изменения прав на публикацию.
3. Проверьте локальное сравнение `/admin/museum-content/compare`, список исчезающих URL и пакет согласования `/admin/museum-content/release-review.json`. Отметки внутреннего редактора **не равны** согласованию музеем.
4. Для локальной диагностики из `apps/cms`: `php artisan museum:preflight --strict`. Строгий экспорт / публикация работают только в утверждённой последовательности с проверкой SHA-256 и архивом предыдущего выпуска. Не выполняйте выпуск в боевой контур до утверждения схемы развёртывания.
5. После согласованного релиза проверьте manifest и публичные HTML, навигацию, ссылки на исходные документы и отсутствие черновиков. Сравните контрольные суммы с подписанным выпуском.

## Сбой, возврат и резервные копии
- Фиксируйте время, идентификатор релиза/manifest, страницу/slug и симптомы, **не** публикуйте персональные данные посетителей в инциденте.
- При неудачном выпуске применяйте только документированную процедуру отката **публичной статики совместно с CSP**; не заменяйте файлы вручную без контрольных сумм.
- Локальные команды `museum:backup`/`museum:restore` относятся к тестовой среде и **не являются** утверждённой резервной копией промышленной СУБД. Для production нужны согласованные RPO/RTO, расписание, резервное хранилище и тест восстановления.
- Платежи и бронирования находятся во внешней системе до согласования интеграции; никакого повторного «списания» по инциденту сайта.
