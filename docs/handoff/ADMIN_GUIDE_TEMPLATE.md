# TZ-315 · Руководство администратора MusBread (рабочая редакция)

**Статус:** проект документации действующей разработки, 17.10.2026. Не утверждён музеем, без адресов боевой CMS, скриншотов окончательной версии и актов обучения. Не заменяет проект сетевой инфраструктуры.

## Назначение и границы
- CMS: закрытый Laravel / MoonShine; публичная часть: статический Next.js. Не делайте Laravel, БД, файлы медиа и приватные отчёты доступными через публичный Nginx.
- **Администратор** отвечает за роли, структуру, проверку выпуска, восстановление и эскалацию; **редактор** работает в пределах назначенных разделов. Фактические имена сотрудников и матрица доступа заполняются только заказчиком.
- Адрес административного контура и способ доступа предоставляются музеем: **[указать после развёртывания]**. Никаких реальных логинов/секретов в этом руководстве.

## Учетные записи и доступ
1. Получите согласованный закрытый сетевой доступ и индивидуальную учётную запись. Не передавайте пароль по электронной почте или через общие документы.
2. В закрытом MoonShine используйте ресурсы пользователей и ролей. Назначайте право редактора только на реально закреплённые разделы; проверьте доступ под отдельной тестовой учётной записью. Эти же гранты относятся к событиям раздела; события без раздела доступны только администратору.
3. При кадровых изменениях блокируйте/отзывайте доступ по процедуре музея; проверяйте журнал действий `/admin/museum-activity`.
4. Загрузка документов и медиа требует отдельного контроля прав. Публичная статика не должна давать скачивать неопубликованные файлы.

## Подготовка и выпуск материалов
1. Проверяйте структуру `/admin/museum-sections/tree`, особенно статус родительского раздела и черновики, созданные по ТЗ без источника.
2. На `/admin/museum-content/preflight` проверьте ошибки материалов, событий и внутренних ссылок; редактор может исправить содержимое без изменения прав на публикацию.
3. Проверьте локальное сравнение `/admin/museum-content/compare`, список исчезающих URL и пакет согласования `/admin/museum-content/release-review.json`. Отметки внутреннего редактора **не равны** согласованию музеем.
4. Для локальной диагностики из `apps/cms`: `php artisan museum:preflight --strict`. Строгий экспорт / публикация работают только в утверждённой последовательности с проверкой SHA-256 и архивом предыдущего выпуска. Не выполняйте выпуск в боевой контур до утверждения схемы развёртывания.
5. После согласованного релиза проверьте manifest и публичные HTML, навигацию, ссылки на исходные документы и отсутствие черновиков. Сравните контрольные суммы с подписанным выпуском.

## Сбой, возврат и резервные копии
- Фиксируйте время, идентификатор релиза/manifest, страницу/slug и симптомы, **не** публикуйте персональные данные посетителей в инциденте.
- При неудачном выпуске применяйте только документированную процедуру отката **публичной статики совместно с CSP**; не заменяйте файлы вручную без контрольных сумм.
- Локальные команды `museum:backup`/`museum:restore` относятся к тестовой среде и **не являются** утверждённой резервной копией промышленной СУБД. Для production нужны согласованные RPO/RTO, расписание, резервное хранилище и тест восстановления.
- Платежи и бронирования находятся во внешней системе до согласования интеграции; никакого повторного «списания» по инциденту сайта.

## Действия, публикации и статистика администратора

- Существующая закрытая страница: `/admin/museum-activity`. **Только суперпользователь** MoonShine; роль редактора не видит журнал остальных сотрудников.
- «С даты» и «По дату» включительны. Опциональный ID сотрудника ограничивает только аудит действий. Вывод: число записей, уникальных сотрудников, суточная динамика, типы действий и объектов, 50 наиболее активных сотрудников и 100 последних операций. Интервал ограничен двумя годами.
- Блок «Состояние материалов и разделов CMS» показывает **текущее состояние БД** независимо от фильтра: черновики, ожидающие даты публикации, готовые к следующей выгрузке, снятые по сроку, опубликованные и неопубликованные категории. «Готово к выгрузке» не равно размещению на публичном сервере.
- «Публикации статического сайта» показывает исходы и 20 последних запусков существующей очереди без персональной атрибуции. Успех формирования snapshot не гарантирует выкладку на сервер заказчика.
- Нет гостевых посещений, IP/паролей, отклонённых попыток авторизации и действий до внедрения аудита. Требования к срокам хранения и полноте логирования утверждает музей. Не публикуйте этот отчёт во внешнем контуре.

## Проверка релизов и плановое обновление ПО

На предконтрактном стенде командой `python3 scripts/release_site.py history --dest deploy/local` администратор получает список локальных релизов с подтверждёнными SHA-256, текущей/предыдущей версией и размером. Команда не возвращает текст частных материалов и не переключает опубликованную версию. В GitHub Actions добавлена еженедельная read-only проверка npm production и Composer locked. Патчи выбираются только после согласования совместимости с ТЗ, прав на ПО (включая TinyMCE), тестирования, резервного копирования и разрешённого окна обслуживания. Эта инструкция **не** утверждает параметры серверов музея или политику хранения.

## Контроль кеша при установке CMS

После настройки общего драйвера (например CACHE_STORE=database; Redis возможен только после согласования и развёртывания музеем) администратор проверяет php artisan museum:cache-check --require-shared. Успешная диагностика доказывает чтение/запись в подключённое хранилище и эксклюзивность блокировок в данном окружении. Доступ с каждого worker-host и отказоустойчивость проверяются отдельно, в окружении музея. Диагностика не меняет разделы, записи, логины или публикацию. Не применяйте процессный array-cache для нескольких воркеров.

## Linux backend: проверка Nginx, PHP-FPM и systemd до запуска

Это подготовленные файлы для развёртывания, не работающие серверы музея. Перед включением Nginx выполнить nginx -t на целевом Linux и проверить 404 на приватные URI публичного сайта. Реальную версию FPM и совпадение с Nginx socket проверять через python3 scripts/check_php_fpm.py с параметрами --binary, --expected-listen, --nginx-template (не заменять выводом php --version). Systemd worker содержит ExecStartPre через artisan museum:cache-check --require-shared --require-queue-worker и отказывает без готовой общей очереди/блокировок; штатный рестарт и предупреждения мониторятся в journalctl. Включать только один systemd scheduler timer и worker, не дублировать cron. Отдельно согласовать приватный staging и право записывать его из закрытой CMS: default export в ../web не входит в текущие ReadWritePaths при ProtectSystem=strict. Открывать public webroot на запись запрещено. Только после этого включать службы и проводить музейную приёмку.

## SEO и работа редактора в MoonShine — TZ-229/231/233

Меню сотрудника содержит «Материалы и новости», «Афиша и мероприятия», «Изображения», «Документы», «Проверить перед публикацией». Администратор дополнительно видит системную структуру, редакторские согласования, историю публикации, журналы и демонстрационные обращения. Скрытие пункта в меню не заменяет серверную проверку ролей.

В карточке **материала** доступны отдельные H1, SEO-заголовок и SEO-описание (если пусты, применяются обычное название и анонс). В карточке **события** доступны эти же три поля: H1 может отличаться от названия в афише, SEO title/description используются только на публичной странице события после выгрузки. В карточке **раздела сайта** администратор задаёт SEO title/description и H1 для /guide/<slug>/; черновики и скрытые родительские разделы никогда не переходят в публичный контур. Не утверждать непроверенные даты, должности, объявления или SEO по собственной инициативе.

Предконтрактный сайт остаётся noindex. Отдельное разрешение индексации по MUSBREAD_SITE_APPROVED=true допускается только после приёмки официального контента и договора с музеем. После изменения любого SEO-поля выполнить штатную проверку перед публикацией, экспорт и сверку итогового HTML; простое нажатие «Сохранить» в CMS не обновляет публичный статический сайт.


## Перетаскивание файлов и афиша (TZ-235, TZ-122)

В закрытых «Изображениях» и «Документах» допустим выбор через обычное поле файла или перетаскивание ОДНОГО файла на пунктирную область. Изображения допускаются до 5 МиБ: PNG/JPG/JPEG/WebP/GIF/SVG. Документы — до 15 МиБ: PDF/DOCX/XLSX (старый XLS допустим только в согласованном конвертационном тестовом режиме; для production требуются антивирус и регламент). Интерфейс проверяет формат, размер и показывает имя, но **не загружает ничего автоматически**. Редактор задаёт материал, alt-текст/подпись или название документа, а затем нажимает «Загрузить» — сервер повторно проверяет права, структуру и формат файла. Изображение черновика не становится публичным. Модуль для видео и медиа-права музея требуют отдельного утверждения. На главной афиша строится из проверенной публикации CMS, текущие тестовые события явно обозначены как демонстрационные. Название музея в header/footer единое, подлинный графический логотип не подключён до передачи утверждённых RU/EN исходников.

## Афиша по реальным категориям, медиа и структура публичного сайта (TZ-135–154 / TZ-175/190/252/262)

В карточке события CMS редактор задаёт реальную категорию. Выпадающий фильтр в публичной «Афише» автоматически формируется **только из опубликованных категорий** и работает вместе с «Предстоящие / Архив / Все»; для категорий без событий отображается пустое состояние без фиктивных дат. По /guide/museum-media/ посетитель видит галереи только тех изображений, которые прикреплены к уже опубликованным CMS-материалам и реально вошли в проверенную статическую выгрузку. Закрытая медиатека, черновики и видео без прав не появляются там самостоятельно.

Редактор связывает новости, экскурсии, выставки и события через существующую закрытую форму «Связанные материалы»: экспорт переносит только публичные цели, обратная ссылка из афиши создаётся автоматически. Это выполнение TZ-190 не заменяет **контекстные ссылки внутри текста**, которые нужно расставлять и проверять по смыслу отдельно (TZ-176 частично).

Перед каждым релизом выполнить `python3 scripts/audit_structural_tz.py apps/web/out` и полный браузерный регресс при ширинах 320px и 1440px: все реальные страницы должны иметь breadcrumb, каркас header/main/footer, контакты и VK/MAX. Новые страницы автоматически проверяются в CI. Статус 🟢 — технический результат, а не согласование музейной айдентики, фотографий или веб-доступа.

## Текущие выставки и доступные описания фото (TZ-163/194/195)

Публичный список «Текущие выставки» строится из опубликованных записей «Афиши» с категорией «Выставка». Редактор указывает настоящие даты начала и окончания — событие считается текущим **только в этом интервале включительно**, будущее отображается отдельно. Не называть демонстрационные события реальным расписанием музея.

В закрытой медиатеке каждое изображение получает **краткий alt не более 125 символов**: названия «картинка», «фото», «изображение», «графика» не заменяют описание объекта, а форма и сервер откажут в сохранении. Полный текст для сложного изображения (схема, график, карта, диаграмма) вносится в отдельное поле «Развёрнутое описание», до 3000 символов; на публичной странице он выводится под изображением обычным текстом. Старые материалы без этого поля сохраняются без изменения. Проверять alt глазами по исходной фотографии, не доверять автоматической подсказке как распознаванию. После редактирования запустить preflight, export и аудит доступности публичной сборки; экспорт со старым некорректным alt блокируется.

## Управление метаданными на фиксированных маршрутах (TZ-179/185–187)

Материалы, новости, экскурсии, выставки, документы, события и существующие разделы редактируются **в их обычной карточке**: H1, SEO-заголовок и SEO-описание независимы от названия в списке. Для утверждённых EN-переводов есть отдельный английский H1 наряду с SEO title/description. Не создавать альтернативную запись SEO статьи в административном справочнике.

Главная /, поиск /search/, афиша /events/, списки /news/, /museum/, /excursions/, /exhibitions/, /documents/ и справочные /guide/<slug>/ редактируются **администратором** в MoonShine → «SEO фиксированных страниц». В поле «Путь» вводится точный адрес, остальные три поля независимы; статус «Черновик» оставляет действующие значения неизменными, «Утверждено для статической выгрузки» разрешает экспорт. Если у /guide/ есть отдельный опубликованный CMS-раздел, SEO его карточки имеет приоритет. У всех форм остаётся fallback на обычный заголовок, если SEO-поле пусто. Нельзя менять служебные /admin/, /media/, /en/, URLs конкретных новостей и событий из этого справочника.

Контроль актуальности: редакторы меняют материал, статус и сроки опубликования только в пределах назначенных разделов, администратор видит все. Перед выпуском проверить preflight, сравнение версий и текущий административный release-review; изменение SEO меняет хеш снимка и требует новой проверки. **Сохранение в CMS не обновляет публичный статический сайт**: нужен штатный export/release. Контент и заголовки должны быть подтверждены музеем до открытия индексации.

## Генерация title, клавиатура и видимый фокус (TZ-189/208–210)

Для внутренних ссылок готовых материалов, событий и разделов приложение автоматически формирует добавочное описание назначения `title`, а для нативных ссылок — действия по телефону, почте, внешним ресурсам и якорям. Не заменяйте **видимое название ссылки** пустым текстом/иконкой только потому, что `title` теперь есть: он не гарантируется всем устройствам и вспомогательным технологиям. При необходимости редактор вправе указать свой title внутри защищённого TinyMCE; он сохраняется. Любое изменение публичных маршрутов или включение новой группы разделов CMS должно сопровождаться проверкой `python3 scripts/audit_link_titles.py apps/web/out` и отдельным аудитом внутренних переходов.

Пользователь должен достигать каждого действующего элемента Tab/Shift+Tab, переходить по ссылкам Enter, открывать стандартные `details/summary` Enter или Space, управлять поиском стрелками/Enter/Escape. Подсветка фокуса не скрывается на светлом или тёмном фоне, работает в режиме слабовидящих и forced colors. Не вводите `tabindex>0` и кликабельные `div` без клавиатуры. Нативный выбор из `select` дополнительно проверить руками в Safari/Chrome/Windows и на смартфоне; synthetic keyboard в headless macOS не воспроизводит OS popup полностью. Новые слайдеры требуют отдельных тестов до готовности. После изменения фирменной палитры необходим повторный визуальный контрастный аудит.

## Навигация при переходе на дерево разделов CMS и адаптивная вёрстка (TZ-136/147/176/237/242)

После включения нового CMS-дерева **меню** строится только из опубликованных разделов и не восстанавливает старые ветки самовольно. Шесть известных справочных страниц — контакты, доступность, планирование посещения, билеты, документы и возвраты — временно доступны как **неиндексируемые справки** даже если музей ещё не добавил их в CMS; тексты и источники помечены предварительными. Такая справка не становится опубликованным разделом музея. У отсутствующего родителя не создаётся фальшивая хлебная крошка. Перед каждым выпуском обязательны audit_static_navigation.py для всех реально собранных ссылок и real CMS export QA: раньше проверялось только наличие title, теперь строго проверяются URL и фрагменты.

На всех 78 реальных страницах прототипа проверять 320/390/768/1024/1440 px: отсутствие горизонтальной прокрутки, header/main/footer, доступные мобильное меню и поиск/афишу. Проверить физически после утверждения музеем айдентики и наполнения. Нельзя публиковать музейные видео/баннеры без оригиналов и прав, выдавать плагиат за фирменную графику или вставлять несогласованные смысловые ссылки в контент (TZ-136/147/176/242 пока частичны).

## Путь посетителя и поисковая навигация (TZ-245/246/249)

Главная и /search/ имеют одинаковый блок «Быстрые переходы» с семью ссылками: как добраться, билеты/льготы, афиша, экскурсии, доступность, контакты, документы. Названия маршрутов не означают, что музей утвердил наполнение или платёжные сценарии: до согласования используются только открытые справочные источники, а в афише демонстрационные данные помечены явно. Поиск использует исключительно опубликованный snapshot, индексирует текст материалов/названия/файлы, при отсутствии запроса поясняет условие минимум двух символов, при нуле результатов показывает переход к задачам. Ссылки нельзя делать видимыми только при наведении: навигационные/контентные ссылки подчеркнуты, большие CTA ≥44 CSS px и у них есть контрастный фокус. После редакторских изменений запускать E2E `tz245-249-visitor-journeys.spec.ts` и статический аудит реальных путей.

В `docs/research/UX_PROTOCOL.md` остаётся обязательный отдельный настоящий UX-процесс: 2 раунда по ≥5 участников, измеренный Completion Rate ≥85%. Автоматические тесты маршрутов — не реальные люди, не оценка понятности музейного языка и не положительный итог UX-раунда.

## Контактные сведения и условная боковая навигация (TZ-257/261)

Официальные контакты музея (адрес, метро, телефон, телефонная ссылка tel, почта, режим работы, окончание входа, выходной, санитарный день) теперь редактирует **администратор** в MoonShine → «Контакты и часы работы». Карточка должна быть только одна с ключом primary. Статус «Черновик» никогда не изменяет публичную версию. Для «Утверждено к выгрузке» требуется заполнить все девять полей; фальшивые или неполные поля блокируются валидатором. После сохранения необходим штатный export и release; изменение контактов меняет контрольный хеш и появится в административном сравнении версий. До выпуска действуют только прежние датированные справочные сведения. **Перед запуском музей проверяет фактическую актуальность каждого поля; примерные или тестовые данные не публиковать.** Один утверждённый набор используется на главной, в footer, на контактных/посетительских справках и в поиске, а не в разных таблицах.

Боковое меню создаётся автоматически только для опубликованного CMS-раздела, у которого есть опубликованные дочерние узлы. Нельзя вручную дублировать список ссылок, открывать черновики или вводить безосновательное второе дерево. На маленьких экранах этот aside переходит ниже текста. На обычной странице контактов sidebar не появляется. Браузерный тест измеряет симметричные отступы, переполнение и зоны header/content/footer; после утверждения бренда требуется отдельная визуальная проверка, поэтому TZ-251/260 пока частичны.

## Обложки событий из утверждённой медиатеки (TZ-147)

Изображения добавляются только через прежнюю защищённую медиатеку **«Изображения»**: выберите опубликованный материал своего раздела, загрузите разрешённое фото, вручную проверьте содержательный alt (≤125 знаков), при необходимости внесите подпись и подробное описание. В MoonShine → «Афиша и мероприятия» → карточка события появилось необязательное поле **«Обложка»**: выбирайте одно из изображений опубликованного материала *того же редакторского раздела*. Нельзя использовать фото из чужого раздела или черновика; сервер отклонит такое сохранение, даже если подменить отправляемую форму. До утверждения прав на каждую оригинальную фотографию не назначайте её на публичное событие. Если обложка не назначена, остаётся прежняя нейтральная графика, а не новая выдуманная фотография.

Одна утверждённая WebP-копия используется и в материале, и в афише; отсутствие исходника в разрешённом публичном snapshot автоматически выключает обложку. Снятие фото из материала с публикации скрывает обложку при следующей статической выгрузке; удаление фото сбрасывает связь с событием. Подписи/alt/длинные описания переносятся на страницу события; большие фото загружаются lazy, без автозапуска видео. При планировании публикации проверить **сравнение версий и preflight**, затем сделать штатный export и статический release, вручную просмотреть карточку и исходные права. Реальные даты, афиши, авторство и графику обязан подтвердить музей до сдачи.

## Контекстные ссылки и предпубликационная проверка (TZ-176)

В закрытой MoonShine теперь есть пункт **«Подобрать ссылку в текст»**. Там показаны только новости, материалы и события, действительно опубликованные в следующем снимке (включая подтверждённые EN-переводы); черновики, скрытые/истёкшие/будущие URL никогда не выводятся. Найдите относящийся к тексту материал, выделите и скопируйте его адрес из readonly-поля, затем в TinyMCE выделите **осмысленные слова** в абзаце и вставьте URL кнопкой «Ссылка». Не подменяйте это автоматическим модулем «Связанные материалы» и не выдумывайте смысловые связи; редактор утверждает содержимое сам. Предпубликационная проверка блокирует неверные/пустые ссылки, предупреждает о «здесь», «читать», «подробнее» и ссылке на саму страницу. Перед публикацией исправьте предупреждения и запустите `php artisan museum:preflight --strict` и штатный экспорт, затем проверьте статические адреса и фрагменты HTML.

## Нормативные требования TZ-279/280/281 — без ложных сертификатов

Исходный защищённый репозиторий доказывает только некоторые технические меры (закрытая CMS, role ACL, отсутствие автоприёма ПДн, санкционированный контент, CSP), не юридическое соответствие: применимость 126-ФЗ «О связи», 149-ФЗ о защите информации и 390-ФЗ «О безопасности» должен установить заказчик с юристом и специалистом ИБ по договору хостинга, владельцу информации, моделям угроз, реальным правам, журналам, резервным копиям и серверу. Отключённые формы не активировать до одобренного пакета политики. Действующий проверяемый отчёт: `python3 scripts/audit_legal_readiness.py` (`docs/tz-audit/LEGAL_PREAWARD_READINESS.json/.md`). Ни один пункт юридически не принят автоматически.

## TZ-295/308/309 — редактор и контроль применимости

В стандартной карточке TinyMCE есть WYSIWYG и кнопка «Исходный код». Плагин code поставляется локально, без CDN. HTMLPurifier, роли и ограничение разделов сохраняются. GPL-2.0-or-later у TinyMCE runtime требует лицензионного решения или замены перед передачей. Для TZ-295 юридический реестр содержит 8 активных/отключённых/неизвестных функций и поле feature_scope_approved=false, поскольку отсутствие формы не доказывает неприменимость закона к учреждению. При изменении интеграции пересобрать аудит и получить правовое решение музея.

## Строгая публикация ядра (TZ-267)

По умолчанию каждый час используется museum:export --preflight-strict с запретом перекрытия запусков. Если отдельно включена очередь и worker, job PublishMuseumSnapshot также запускает строгий preflight. Критичные ошибки ссылок/контента не изменяют подготовленный JSON/manifest. Фоновый журнал фиксирует статус failed только с классом ошибки. Редактору требуется исправить опубликованный материал, запустить museum:preflight --strict, затем повторить выпуск через штатный защищённый контур. Ручной нестрогий экспорт — только диагностический; он не заменяет процедуры реального релиза. Клиентские серверы, TLS, передача, мониторинг, резервирование и официальное одобрение остаются вне этого локального теста.

## Лёгкий UI, сетка и медиараздел

Публичные шаблоны используют единые CSS-переменные museum-shell-width, museum-gutter, museum-section-gap и museum-layout-gap. При добавлении нового контента, графики или шрифта не прописывать отдельные случайные сдвиги заголовков; после Next build прогонять геометрические Playwright тесты и read-only скрипт scripts/audit_lightweight_ui.py, который запрещает сторонние JS, iframe/autoplay и чрезмерно тяжёлые вложения. Для медиа CMS разрешены только фото опубликованных материалов с проверенным alt и правами. Страница https://muzei-xleb.ru/video — первоисточник, не разрешение скачивать чужие видео. Перед публикацией архивных роликов получить документы о праве, сами оригиналы и музейную приёмку. Фирменная сетка/шрифты и реальные устройства заказчика должны быть утверждены в отдельной UAT.
