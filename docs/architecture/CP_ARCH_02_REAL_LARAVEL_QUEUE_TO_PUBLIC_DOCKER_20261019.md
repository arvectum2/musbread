## В чём принципиальное отличие от предыдущего CP-ARCH-01

CP-ARCH-01 проверял передачу пяти **уже готовых** статических файлов через два Docker-сегмента и откат. В этом сценарии **данные теперь начинаются с реально запущенного обработчика Laravel**, а не с фиктивного JSON и не с прямого вызова метода PHP:

1. В `.local_archive` на **ArvectumSSD** создаётся новая временная SQLite-БД; реальные `php artisan migrate --force` создают Laravel-таблицы, включая таблицы очереди и журнал публикации. В тестовой базе создаются одна опубликованная QA-новость, один **неопубликованный QA-черновик** и одно QA-событие для корректной генерации динамического статического маршрута Next.js. **Ни один из этих материалов не является текстом или новостью действующего музея.**
2. Выполняется настоящая `php artisan museum:queue-export` с `QUEUE_CONNECTION=database`, `CACHE_STORE=database`, `MUSEUM_USE_PUBLISH_QUEUE=true`; проверяется постановка ровно одного задания в `museum-publish`.
3. **Настоящий** `php artisan queue:work database --queue=museum-publish --once ...` исполняет `PublishMuseumSnapshot`, строгий `museum:export --preflight-strict` и формирует одобренные данные. В журналах — `succeeded`, одна попытка, пустые `jobs`/`failed_jobs`, правильный `snapshot_sha256`.
4. **Новый opt-in путь `MUSEUM_QUEUED_EXPORT_STAGING_DIR`** направляет JSON, манифест и все публикуемые media/documents в отдельную закрытую папку, не затрагивая `apps/web/src/data/published.json` и рабочие материалы Next. Если параметр отсутствует, старое поведение сохраняется. Если директория отсутствует, является symlink или находится внутри web/CMS public либо отслеживаемого web/src, задание отказывается выполнять публикацию и записывает статус `failed`.
5. Новый Next.js **собирается заново** во временной копии `apps/web` из настоящего сгенерированного Laravel JSON. Фоновый `postbuild` для миграции настоящего музея отключён **только во временной копии**, потому что его относительный путь не должен изменять основные Nginx/SEO файлы проекта. В сборке появляется `/news/qa-real-laravel-queue-news/index.html`; маршрут черновика отсутствует, у статьи сохраняется `noindex` стенда.
6. Скомпилированная реальная HTML-страница передаётся вместе с пятью музейными статическими файлами из **этой конкретной новой сборки**, через уже проверенные два Docker-сегмента и read-only публичный Docker volume. Промежуточный контейнер получает пакет по внутреннему HTTP, сверяет SHA-256 по независимому sidecar и активирует выпуск. Настоящий Nginx по `127.0.0.1:18089` возвращает **байт-в-байт ту самую HTML-новость**, созданную из Laravel database queue. Изменённый HTML/добавленный PHP отклоняются. Проверяется атомарное переключение тестовой второй версии и возврат исходной.
7. Все временные файлы, SQLite, контейнеры, сети и Docker volume удаляются. Продуктовый сайт, рабочая CMS-БД и DNS не меняются.

## Границы доказательства и что ещё открыто

- **Полноценный Laravel/MoonShine в Docker не развёрнут:** реальные PHP-команды выполняются на Mac mini с временной SQLite. Для передачи собранного пакета внутри закрытого Docker-сегмента используется PHP 8.4 transport surrogate. Это разные части ОДНОГО проверенного локального QA-сценария, а не промышленная интеграция двух хостов музея.
- В тесте редакционная публикация моделируется полем `status=published` при `MUSEUM_ENABLE_APPROVAL_QUEUE=false`. **Настоящее одобрение редактора и 60-минутный SLA по времени именно его решения этим сценарием не подтверждены.** Существующие ACL/explicit-approval PHP feature-тесты остаются самостоятельным доказательством контроля доступа; нужно подсоединить событие редактора к доставке с измерением реального времени.
- `MUSEUM_QUEUED_EXPORT_STAGING_DIR` — **закрытый локальный источник, а не новая публичная CDN/площадка**. Пакет SHA-256 требует отдельно аутентифицированного доверенного канала/манифеста, проверки повтора и контрольных времён. Одного sidecar недостаточно против злоумышленника, способного менять и данные, и хеши.
- Локальный прогон переносит только шесть файлов для быстрого network/worker acceptance, а **не всю** рабочую музейную CMS и 101 PDF. Полная локальная сборка исходного корпуса отдельно прошла HTTP-проверки CP-SEO-06 (881 редирект, 467 исходных HTML, 27 страниц архива, 101 PDF/DOCX, 303 WebP).
- Нет реальной защищённой сети музея, финального домена, HTTPS/TLS-пентеста и production worker/systemd; доступы заказчика нужны после договора. **Нет требования отдельно получать SEO-статистику или согласовывать `www`.**

Формальную матрицу **325 пунктов ТЗ не повышаем только за локальный QA**: 🟢84 / 🟡102 / 🔴139. Для промышленного завершения TZ-104–107 остаются доставка настоящего редакторского approval-события, защищённый канал и реальная проверка условий сети заказчика.
