# Правило разработки MusBread: вначале обязательства исходного ТЗ

Введено по прямому указанию участника закупки 16 октября 2026, до следующего этапа после CP-51D. Относится ко **всем** будущим решениям в MusBread. Источник — описание объекта закупки, приложение №3 извещения №0372200172326000015, построчный первичный реестр `docs/tz-audit/requirements.psv`, матрица `TZ_FULL_MATRIX.md`. Текст исходного DOCX при споре имеет приоритет перед нашей интерпретацией реестра.

## Обязательная процедура перед **каждым** новым действием по функциональности

1. **Найти прямое требование в первичном ТЗ** и указать `TZ-NNN`, номер подпункта и строки исходного текста (по реестру). Для интеграций/конкретных экранов связать действующие обязательства с оригинальной формулировкой, а не искать оправдание готовому решению.
2. **Проверить, что уже реализовано и проверено на ArvectumSSD**: не пересоздавать готовые функции и не считать частичное совпадение выполненным пунктом.
3. **Определить приоритет по ТЗ**: сначала незакрытые блокирующие P0, затем P1, затем P2, если не требуется обеспечивающая техническая работа для ближайшего обязательного пункта. Документировать препятствия и получаемые от заказчика данные. Реальные интервью, утверждения, передача прав, печатные макеты и UAT не заменяются имитациями.
4. **Если функция не требуется ТЗ**, отложить её в список необязательных улучшений. Делать лишь при явном распоряжении пользователя либо если без неё нельзя исполнить конкретный пункт ТЗ и доказана зависимость. Это относится, в частности, к фильтрам внутренней очереди редакторских задач CP-52D: требование к таким фильтрам в первичном реестре **не найдено**; приоритет отдан TZ-154.
5. **Реализовать только соответствующий scope**, включая отрицательные случаи, приватность и тесты. ТЗ предписывает возможности WYSIWYG/HTML-редактирования и CMS MoonShine, **но не продукт TinyMCE**. Текущий TinyMCE — выбор реализации, не требование заказчика; решение об инструменте принимаем исходя из лицензии, достаточности функций и безопасной миграции, не выдавая его за обязательный по ТЗ. Не утверждать, что прототип без документов/согласования клиента уже «сдан».
6. **Подтвердить результат**: локальная и CI-проверка, обновлённая строка `requirements.psv` и генерация `python3 scripts/render_tz_audit.py`; чекпоинт, ссылки на коммит/тесты, точное состояние `Да`/`Частично`/`Нет` и что осталось от музея. Сохранять основную работу непосредственно в `/Volumes/ArvectumSSD/arvectum/repos/musbread`, выполнять зеркалирование GitHub → GitVerse.

## Реальный незакрытый объём

После TZ-154 (исторический срез) — **325** атомарных обязательств; `Да` **15**, `Частично` **116**, `Нет` **194**, из них P0 **163** строк. Эти числа не равны проценту завершения контракта и не учитывают приёмочные испытания/права/утверждения. Правило действует также для всех будущих CP-XX: не писать на основе удобства разработчика, а закрывать прежде всего требования закупки.

## Матрица-навигатор (325 требований; версия 16.10.2026)

- [`tz-audit/TZ_EXECUTION_MATRIX.html`](tz-audit/TZ_EXECUTION_MATRIX.html) — автономный светофор с 19 группами, поиском и фильтрами; без CDN и обращений к музею.
- [`tz-audit/TZ_EXECUTION_MATRIX.md`](tz-audit/TZ_EXECUTION_MATRIX.md) — читабельная полная матрица всех атомарных обязательств.
- [`tz-audit/TZ_EXECUTION_MATRIX.csv`](tz-audit/TZ_EXECUTION_MATRIX.csv) — таблица для Excel/Numbers с номером очереди, внешней зависимостью, следующим шагом, приоритетом и ссылкой на первичный пункт.

**Расчёт очереди:** 128 следующих внутренних задач, которые можно начинать без ещё не выданных доступов/утверждённого брендбука. Ранг внутри очереди определяется P0 → P1 → P2, затем фазой существующей дорожной карты и исходным TZ-ID. Эти номера динамические, они показывают следующий **доступный шаг разработки**, но не обещают сдать весь пункт до будущего согласования. Остальные 182 незакрытых пункта помечены как ожидающие конкретного внешнего условия/контрактной стадии. После изменения `requirements.psv` или списка немедленно доступных шагов `CAN_START_NOW` выполнять `python3 scripts/build_tz_execution_matrix.py` и `python3 -m unittest tests.test_tz_execution_matrix -q`; тест проверяет 325 ID, тексты, светофор, статусы, отсутствие двойных номеров и идентичность CSV/JSON/HTML/Markdown.

## Актуализация операционной очереди 16 октября

Первые задачи TZ-072/076/077/085/087/088/111/228/230/234/236 прошли проверку по ТЗ и реализованный локальный объём, их следующие существенные шаги зависят от клиента/инфраструктуры. После каждого прохода **обновлять `requirements.psv` (реальный статус и доказательства)**, фиксировать новую внешнюю зависимость в `WAITING_ON_CUSTOMER_AFTER_LOCAL_WORK` генератора и снова выстраивать очередь. Нельзя менять зелёный статус автоматически по факту прохождения теста: без UAT это лишь часть обязательств. Точный актуальный счётчик — в сгенерированной матрице, не в старом срезе выше.

## 29.10.2026 — обязательный Spec Kit source gate (v1.2.4)

Эталон реализации — Tender Agent Spec Kit 1.2.4 с integration `none`: `.specify/memory/constitution.md`, `specs/001-contract-tz-traceability/spec.md`, `plan.md`, `tasks.md`. Не создаём второго агента или альтернативную дорожную карту. Прямое техническое применение:

1. **Перед любой интерпретацией:** `python3 scripts/check_speckit_tz.py --show TZ-104` — выводит полный дословный текст указанной строки *из проверенного оригинала*, номер и SHA; вместо `TZ-104` указать любой ID 001–325. `--verify-source` проверяет все 325 ID и цитаты с закрытым оригиналом. Не пользоваться только инженерным резюме из TSV/PSV.
2. **Спецификация:** `specs/001-contract-tz-traceability/spec.md` — 325 ID с пунктами, физическими строками, точными выдержками и отдельными инженерными резюме. `source-map.json` закреплён отдельным контрольным SHA. Полный нормативный текст в закрытом исходнике; выдержка может быть короче полного пункта.
3. **При каждом изменении:** записать TZ-ID и его полный исходный текст, что прямо предписано, что является инженерной интерпретацией, что зависит от согласования. Для новых bounded-функций создавайте отдельные нумерованные `spec.md` / `plan.md` / `tasks.md`, ссылаясь на этот базовый реестр.
4. **Проверка:** `python3 scripts/check_speckit_tz.py --check` — офлайн структурная проверка для GitHub CI; **она не удостоверяет первоисточник**. На Mac mini перед принятием изменения обязательно `--verify-source`. При изменении статуса существующего реестра выполняйте `--render`; источник и 325 ID не перегенерировать автоматически.
5. **Спорные трактовки:** `specs/001-contract-tz-traceability/interpretation-review.md`. В частности, п. 2.2.3.4 содержит «каждый час **или** по событию», поэтому разделение TZ-104/TZ-105 нельзя автоматически трактовать как обязательство выполнить оба независимых варианта. Источник имеет приоритет перед нашими summary и ADR.

Spec Kit не заменяет требования подписанного приложения, официальную приёмку, испытания на двух ВМ и сроки/объём действующего контракта.
