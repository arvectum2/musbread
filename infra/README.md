# MusBread · развёртывание (шаблоны до победы)

**Статус: не установлено в музее.** Реальные адреса, домен, сертификаты, сеть, БД, разрешения, серверы и поставщик билетов неизвестны. Никакие конфигурации здесь нельзя просто копировать в production без обследования и согласования с заказчиком.

## Сегменты
1. Закрытый сегмент: Laravel/PHP 8.4/MoonShine, SQL и медиатека, пользователь `musbread`. `infra/nginx/private-cms.conf` для временного loopback-демо, не общедоступная конфигурация.
2. Публичный сегмент: Nginx с **только статическими HTML/CSS/JS/WebP**, без `fastcgi_pass`, `proxy_pass`, CMS и БД. `infra/nginx/public-static.conf` слушает только loopback 127.0.0.1:18080. После согласования будет организован HTTPS на публичном фронте с сертификатом заказчика.
3. Передача из закрытого в публичный сегмент не реализована до получения подтверждённого сетевого канала. Использовать localhost-порты на общем компьютере — не означает соответствие физической сегментации.

## Требуемое Linux окружение
PHP 8.4 FPM, Nginx, Linux systemd, приватная БД и защищённая сеть, доступность которых заказчик должен подтвердить. Пути `/srv/musbread`, `/run/php/php8.4-fpm.sock` и `/etc/musbread/cms.env` — **пример**, они не соответствуют никакому реальному серверу музея.

### systemd
- `musbread-scheduler.timer`: ежеминутно запускает Laravel Scheduler.
- `musbread-publisher.service`: worker для очереди `museum-publish`, ограничение выполнения 600 секунд.
- Перед включением очереди установить `MUSEUM_USE_PUBLISH_QUEUE=true`, `DB_QUEUE_RETRY_AFTER >=900`, выбрать надёжный драйвер блокировок, задать `QUEUE_CONNECTION=database` или согласованный другой драйвер и мониторинг. `queue:failed`, мониторинг ошибок и резервирование требуется до запуска.
- Демонстрационный `demo_publish.sh` и dev-пути в коде нельзя использовать как промышленную доставку из изолированного контура.

### Регламент резервного копирования — подготовка
База данных и содержимое закрытой медиатеки — обязательные данные для восстановления. **Движок БД заказчика пока неизвестен**, поэтому копирование работающего файла БД или `rsync` каталога данных без согласованного механизма не предлагать. После обследования выбрать транзакционно консистентное резервирование (например pg_dump для PostgreSQL, если он используется), зашифрованное хранение отдельно от сервера и регламент срока хранения. Тест восстановления должен поднять чистый стенд и выполнить миграции, восстановление пользователей/контента, проверку SHA-256 медиа, тестовый экспорт, сравнение публичной версии и rollback.

Публичный контур может быть восстановлен из заверенного архивного релиза; обязательно сохранить журнал версий и инструкции. Испытания резервного копирования на реальной инфраструктуре — **после победы и письменного разрешения**.

## Приёмочный чек-лист
- [ ] Подтверждена физическая/сетевая изоляция двух контуров
- [ ] TLS и доверенные адреса согласованы музеем
- [ ] Приватная БД и CMS не доступны из внешней сети
- [ ] Worker запущен, таймаут/повторы/отказоустойчивость проверены
- [ ] Публикация по требованию и не реже раза в час
- [ ] Проверено восстановление БД, медиа, релизов и права доступа
- [ ] Разрешённый пентест + протоколы нагрузочного тестирования

## Security headers / CSP — подготовлено до победы

Генератор scripts/build_csp.py вычисляет SHA-256 каждого inline-script во всех HTML-страницах готовой сборки Next.js и формирует заголовок Content-Security-Policy без unsafe-inline для JavaScript и без unsafe-eval.

После каждой сборки запустить:
    python3 scripts/build_csp.py apps/web/out --output /tmp/musbread-csp.conf

Критично: политика связана с конкретной версией статической сборки. Нельзя обновлять HTML без соответствующего CSP или откатывать релиз, не пересчитав политику и не перезагрузив Nginx. Генератор не очищает пользовательский HTML и не заменяет HTMLPurifier / sanitize-html. Для CSS пока разрешено style-src 'self' 'unsafe-inline' (требуется текущему интерфейсу), для JavaScript это запрещено. CSP растёт с числом страниц; перед промышленным запуском оценить размер заголовка и при необходимости перейти к отдельным политикам для маршрутов либо к выносу inline-кода.

Конфигурацию infra/nginx/http-rates.conf включать на уровне http Nginx: лимиты считаются только для POST. Laravel отдельно ограничивает MoonShine login до 8 POST/мин с IP, upload до 30 POST/мин с IP; бюджет надо проверить для реальной NAT/сетевой схемы. Rate-limit не заменяет изоляцию CMS.

CI проверяет nginx -t и localhost HTTP smoke (CSP/nosniff, отсутствие /admin и .php). Реального TLS и независимого пентеста пока нет.

## Контроль технологических пунктов TZ-223/224/225 (17.10.2026)

- Публичный Nginx обязан отказывать в выдаче /database, /bootstrap, /config, /private, /storage, /vendor, /admin, /api и исполняемого PHP. Существующий шаблон и Linux CI проверяют эти ограничения. На Mac mini одноразовый Linux Alpine контейнер прошёл nginx -t и вернул 404 для тестового /database/private.txt, хотя файл реально лежал внутри временного публичного root.
- Для Linux PHP-FPM 8.4+ предусмотрен read-only аудит scripts/check_php_fpm.py. Вызвать его на целевом сервере с фактическим бинарём FPM, ожидаемым Unix socket и infra/nginx/private-cms.conf. Исторически локальный macOS FPM 8.4.26 проходил проверку версии, но с 21.10.2026 он уязвим (PHP2Shell), поэтому gate теперь требует 8.4.27+ или 8.5.12+. Его pool использует TCP, поэтому НЕ подтверждает сокет /run/php/php8.4-fpm.sock на Linux.
- Системный publisher worker теперь перед запуском требует безопасный database queue, включённый MUSEUM_USE_PUBLISH_QUEUE, DB_QUEUE_RETRY_AFTER >=900 и рабочие общие блокировки Laravel. Сервис возобновляет работу после штатного выхода; повторные быстрые отказы ограничены. Systemd service/timer прошли systemd-analyze verify внутри одноразового Linux-контейнера.
- Важный блокер: Laravel museum:export по умолчанию пишет в соседний ../web, а ProtectSystem=strict разрешает запись только в storage и bootstrap/cache закрытого CMS. Без согласованного ПРИВАТНОГО каталога staging и транспорта экспорта на public Nginx запускать production worker/таймер нельзя. НЕ выдавать CMS запись в публичный webroot для устранения этого расхождения. Решение зависит от сетевой схемы и файловой системы заказчика.
- Любая проверка контейнера/локальных конфигов — не испытание боевой инфраструктуры. Требуются назначенные Linux-хосты, утверждение сетевой изоляции и TLS, реальный пул FPM, systemd enable/restart/stop/UAT, журнал ошибок, восстановление и разрешённое тестирование безопасности.

Подробная схема: docs/TZ223_225_SERVER_INFRA_GATES.md.

### PHP2Shell (CVE-2026-109618 / CVE-2026-109619, 21.10.2026)

Перед запуском CLI, PHP-FPM, очередей и развёртыванием запускать `python3 scripts/check_php_runtime.py` **на том сервере/в том контейнере**, где реально работает PHP. Для FPM дополнительно использовать `scripts/check_php_fpm.py` с реальным бинарём и ожидаемым сокетом. Минимумы: PHP 8.2.35, 8.3.36, 8.4.27, 8.5.12; неподтверждённые ветки отклонять. Проверка PHP на Mac mini, успешный CI или актуальный `composer.lock` не доказывают защищённость PHP на хостинге музея. Docker-образы с PHP 8.4.26 требуют обновления перед повторными тестами.
