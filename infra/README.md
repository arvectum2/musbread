# MusBread · развёртывание (шаблоны до победы)

**Статус: не установлено в музее.** Реальные адреса, домен, сертификаты, сеть, БД, разрешения, серверы и поставщик билетов неизвестны. Никакие конфигурации здесь нельзя просто копировать в production без обследования и согласования с заказчиком.

## Сегменты
1. Закрытый сегмент: Laravel/PHP 8.4/MoonShine, SQL и медиатека, пользователь `musbread`. `infra/nginx/private-cms.conf` для временного loopback-демо, не общедоступная конфигурация.
2. Публичный сегмент: Nginx с **только статическими HTML/CSS/JS/WebP**, без `fastcgi_pass`, `proxy_pass`, CMS и БД. `infra/nginx/public-static.conf` слушает только loopback 127.0.0.1:18080. После согласования будет организован HTTPS на публичном фронте с сертификатом заказчика.
3. Передача из закрытого в публичный сегмент не реализована до получения подтверждённого сетевого канала. Использовать localhost-порты на общем компьютере — не означает соответствие физической сегментации.

## Требуемое Linux окружение
PHP 8.4 FPM, Nginx, Linux systemd, приватная БД и защищённая сеть, доступность которых заказчик должен подтвердить. Пути `/srv/musbread`, `/run/php/php8.4-fpm.sock` и `/etc/musbread/cms.env` — **пример**, они не соответствуют никакому реальному серверу музея.

### systemd
- `musbread-scheduler.timer`: ежеминутно запускает Laravel Scheduler.
- `musbread-publisher.service`: worker для очереди `museum-publish`, ограничение выполнения 600 секунд.
- Перед включением очереди установить `MUSEUM_USE_PUBLISH_QUEUE=true`, `DB_QUEUE_RETRY_AFTER >=900`, выбрать надёжный драйвер блокировок, задать `QUEUE_CONNECTION=database` или согласованный другой драйвер и мониторинг. `queue:failed`, мониторинг ошибок и резервирование требуется до запуска.
- Демонстрационный `demo_publish.sh` и dev-пути в коде нельзя использовать как промышленную доставку из изолированного контура.

### Регламент резервного копирования — подготовка
База данных и содержимое закрытой медиатеки — обязательные данные для восстановления. **Движок БД заказчика пока неизвестен**, поэтому копирование работающего файла БД или `rsync` каталога данных без согласованного механизма не предлагать. После обследования выбрать транзакционно консистентное резервирование (например pg_dump для PostgreSQL, если он используется), зашифрованное хранение отдельно от сервера и регламент срока хранения. Тест восстановления должен поднять чистый стенд и выполнить миграции, восстановление пользователей/контента, проверку SHA-256 медиа, тестовый экспорт, сравнение публичной версии и rollback.

Публичный контур может быть восстановлен из заверенного архивного релиза; обязательно сохранить журнал версий и инструкции. Испытания резервного копирования на реальной инфраструктуре — **после победы и письменного разрешения**.

## Приёмочный чек-лист
- [ ] Подтверждена физическая/сетевая изоляция двух контуров
- [ ] TLS и доверенные адреса согласованы музеем
- [ ] Приватная БД и CMS не доступны из внешней сети
- [ ] Worker запущен, таймаут/повторы/отказоустойчивость проверены
- [ ] Публикация по требованию и не реже раза в час
- [ ] Проверено восстановление БД, медиа, релизов и права доступа
- [ ] Разрешённый пентест + протоколы нагрузочного тестирования
